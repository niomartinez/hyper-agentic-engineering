# Engineering foundation

Use the smallest complete implementation that satisfies the task and its verification needs. Current user and repository instructions take precedence; team-specific rules stay scoped to that project.

- Understand before editing. Inspect the current code, behavior and conventions. State consequential assumptions and resolve uncertainty that would change the implementation; do not turn routine choices into approval requests.
- Keep changes focused. Reuse existing code, standard tools and installed dependencies. Avoid speculative features, unnecessary abstractions and unrelated cleanup. Prefer interfaces that hide real complexity.
- Define observable success. Reproduce bugs, identify their cause, and verify the changed behavior. Choose meaningful tests for the risk; avoid tests that merely mirror implementation. Preserve validation, security, accessibility and data-loss handling.
- Work with other contributors. Inspect working-tree changes, preserve their edits, and verify ownership, branch and environment before acting. An account switch does not change authorship or project scope.
- Keep context lean. Read the matched project note and relevant source first. Load one specialized method and only its needed references; do not import an entire skill library or conversation into every turn.
- Use the relevant workflow. For debugging, tests, architecture, review, research or design, consult hae-engineering's task reference and route to a relevant installed skill. Existing team methods win. Full community Karpathy guidelines and graph analysis are explicit opt-ins.
- Persist decisions at meaningful milestones. The main chat interprets remember/override requests, then local code saves approved prose. Ordinary replies need no note or second generative worker. Keep uncertain evidence separate from verified status and policies.
- Make cutoffs resumable. Use the repository's handoff convention, otherwise docs/handoffs/YYYY-MM-DD-topic.md. Record the task, branch/commit, decisions, actual checks, unfinished step, next action and known owner. Include only team-approved project information.
- Report outcomes with evidence and remaining limits. Concision must preserve exact names, paths, commands and qualifications. Documents, code comments and team handoffs use normal prose. Optional lean style never reduces required work.
- Evaluate new techniques against a baseline. Use ordinary code for exact rules. Consider optional semantic tools such as Jev only for relevant bounded decisions, with explicit data scopes, measured quality/cost and rollback. Installation does not authorize paid services, publication or unrelated external changes.

This is original generalized guidance informed by the author's working practices and the catalogued community Karpathy-inspired, Matt Pocock and Ponytail sources. It is not an official Karpathy release or a copy of those skill bundles. It carries no personal accounts, employer exceptions, model mandates or publishing permissions.
